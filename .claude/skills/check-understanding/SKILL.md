# 理解度チェック

インターン生が `task/` 配下のタスクを完了し、PRを作成する前に自分の理解度を確認するためのスキル。

このスキルの目的は「テストで採点すること」ではなく、**本人が自分の理解の穴に気づき、次の学習につなげること**。コードが動いていても「なぜそう書いたのか」を説明できないことはよくある。それを責めるのではなく、可視化して次のアクションにつなげるのがゴール。全体を通して、面接官ではなく伴走するメンターのトーンで進めること。

## 進め方の全体像

1. 取り組んだタスクを特定する
2. 差分とタスクの学習目標を照らし合わせてコードを分析する
3. 実装内容に即した質問を対話形式で行う(4〜6問)
4. レポートを生成してファイルに保存する

## 1. タスクの特定

このリポジトリでは、インターン生ごとに `<GitHubユーザー名>/main` という個人用ベースブランチがあり、そこから `<ユーザー名>/task1` のような命名のfeatureブランチを切ってタスクに取り組む運用になっている。つまり現在のブランチ名から**ユーザー名(=比較先)とタスク番号の両方**が読み取れる。

手順:

- `git branch --show-current` で現在のブランチ名を確認する
- ブランチ名が `<ユーザー名>/task<N>` の形なら、比較先は `<ユーザー名>/main`、タスクは `task/N-*.md` と推測できる
- 差分の比較先はリポジトリの `main` ではなく、必ず**本人の `<ユーザー名>/main`** を使うこと。リポジトリの `main` と比較すると、本人の過去タスクの実装など今回のタスクと無関係な変更が混ざり、分析がずれる
- `git diff <ユーザー名>/main...HEAD` と `git log <ユーザー名>/main..HEAD --oneline` で差分を確認する(ローカルにベースブランチがない場合は `origin/<ユーザー名>/main` を使う)
- コミットされていない変更しかない場合は `git diff` / `git status` も見る
- 差分の内容がタスクファイルの「タスク内容」と合っているかを軽く照合したうえで、「タスク3(メッセージ一覧を更新できる)の理解度チェックを、`<ユーザー名>/main` との差分で行いますね。よいですか?」のように**必ず本人に確認**してから進める
- ブランチ名が上記の形式でない、ベースブランチが見つからない、ブランチ名のタスク番号と差分の内容が食い違うなど、推測に自信が持てない場合は、素直に本人へタスク番号とベースブランチ名を質問する
- 差分がまったくない場合は、実装がまだかブランチが違う可能性を伝えて終了する

## 2. コード分析

特定したタスクファイル(`task/N-*.md`)を読み、「タスク内容」と「学び」を把握する。「学び」がこのチェックの評価軸になる。

そのうえで差分を読み、次の観点でメモを取る(このメモは後の質問作りとレポートの根拠に使う):

- 学習目標それぞれに対して、実装のどこが対応しているか
- 本人が何かを**選択した**箇所はどこか(例: SnackbarかダイアログかToastか、Result型か例外か、テストダブルの種類、状態の持ち方)。選択には理由があるはずで、理由を説明できるかが理解度の良い指標になる
- 動くけれど理解が浅そうな兆候(不要なコードの残留、過剰な防御、スタイルが急に変わる箇所など)

## 3. 対話形式の質問

コード分析を踏まえて、**その人の実装に即した具体的な質問**を4〜6問作る。「Snackbarとは何ですか」のような一般知識クイズにしないこと。一般論は検索やAIで答えられてしまい、本人の理解を測れない。「あなたのこのコードは」と特定できる質問だけが理解度のシグナルになる。

質問は次の3タイプを混ぜる:

- **意図**: なぜそう書いたか。「エラー表示にSnackbarを選んだ理由を教えてください。ダイアログと比べてどんな違いがありますか?」
- **代替案**: 別の方法との比較。「ここでResult型を使っていますが、例外をthrowする方法と比べたメリット・デメリットは何だと思いますか?」
- **挙動**: 変えたらどうなるか。「もしこのviewModelScopeをやめて別のスコープにしたら、画面回転時に何が起きますか?」

進め方のルール:

- **1問ずつ**出し、回答を待ってから次へ進む
- 回答の途中で正解を教えたり評価を口にしたりしない。理由: 先に答えを見せると後の質問への回答が誘導され、レポートの精度が下がる。「ありがとうございます、次の質問です」程度の相槌で淡々と進める
- 「わかりません」は責めない。わからないことがわかるのはこのチェックの成果そのもの。すぐ次の質問へ進む
- 回答が実装の実態とずれている場合(例: コードはtry-catchなのにResult型の説明をする)は、レポートの重要な根拠になるのでメモしておく
- 回答が一般論の丸写しに見える場合は、1回だけ「あなたのコードのこの行では具体的にどうなりますか?」と実装に引き寄せて深掘りしてよい

## 4. レポート生成

質問が終わったら、コード分析と回答の両方を根拠にレポートを作る。

評価は学習目標(「学び」の各項目)ごとに3段階:

- ✅ **しっかり理解** — 実装も説明も一貫している
- 🟡 **おおむね理解** — 動くものは作れているが、説明があいまいな部分がある
- 🔺 **要復習** — 実装と説明がずれている、または説明できなかった

必ず**根拠**を添える。「コードのどこ」「どの質問へのどの回答」から判断したかが書かれていないレポートは、本人が復習ポイントを特定できず役に立たない。

### レポートのテンプレート

```markdown
# 理解度チェックレポート: タスクN <タスク名>

- 日付: YYYY-MM-DD
- ブランチ: <ブランチ名>

## サマリー

(2〜3文。全体傾向と一番伝えたいこと)

## 学習目標ごとの評価

### <学び1> — ✅/🟡/🔺

- **理解できている点**: (根拠つきで)
- **理解があいまいな点**: (根拠つきで。なければ省略)

### <学び2> — ✅/🟡/🔺
...

## 良かった点

(コードや回答で光っていたところ。最低1つは見つけること)

## 次のステップ

(要復習の項目に対する具体的なアクション。タスクファイルのヒントや参考情報のリンクを再掲すると親切)
```

### 保存

- `date +%Y%m%d` で日付を取得し、`reports/understanding-check/task<N>-<YYYYMMDD>.md` に保存する(ディレクトリがなければ作る)
- 保存後、レポート全文を会話にも表示し、保存先パスを伝える
- レポートをコミットするかどうかは本人とメンターの運用に任せる。勝手にコミットしない
